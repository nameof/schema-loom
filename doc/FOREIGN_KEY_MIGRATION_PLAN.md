# 外键迁移支持方案与实施计划

## 1. 目标与边界

外键迁移分为两个阶段：

1. 结构阶段：读取多张表的外键元数据，建立依赖图，完成建表、索引和外键创建。
2. 数据阶段：在结构阶段完成后迁移数据，并按依赖关系处理写入顺序和约束校验。

第一阶段不改变现有 `JdbcTableTarget` 单表数据写入 API，新增独立的多表结构迁移入口。这样可以避免把跨表编排逻辑塞入单表 Target。

## 2. 当前基础与缺口

- `ForeignKeyInfo` 和 `DatabaseMetadataService` 已能提供引用表、列、更新规则和删除规则。
- `JdbcTableTarget.prepare()` 只接收一张表，无法获得同批次表集合，因此不能进行拓扑排序。
- `DatabaseDialect` 尚无外键创建/删除 SQL 生成接口。
- 字段映射必须同步转换本地约束字段；引用表和引用列的跨表改名需要由更高层的多表映射计划处理。

## 3. 建议架构

```text
DatabaseMetadataService
        |
        v
SchemaMigrationPlan  -- 表定义、目标名称、迁移策略
        |
        v
ForeignKeyDependencyPlanner
  - 校验表名和引用关系
  - 拆分强连通分量
  - 输出建表顺序、外键延后列表、删除顺序
        |
        v
SchemaMigrationExecutor
  - 创建表（暂不包含外键）
  - 创建索引
  - 添加/删除/重建外键
        |
        v
DatabaseDialect
  - foreignKeySql
  - dropForeignKeySql
```

规划器是通用图算法，不放入方言；方言只负责生成数据库特定 SQL。

## 4. 执行流程

### 4.1 CREATE/APPEND

1. 收集本批次所有普通表元数据，过滤 VIEW。
2. 校验每个外键的引用表、列数量和目标范围。
3. 构建“引用表 -> 被引用表”的依赖图。
4. 对无环部分执行拓扑排序；对循环部分按强连通分量分组。
5. 创建所有表时不生成外键。
6. 创建索引和表/列注释。
7. 按外键定义比较结果执行：等价则跳过，不一致则按策略失败或重建。

### 4.2 REPLACE

1. 先读取目标端外键关系。
2. 按逆依赖顺序删除外键和表；循环分量需要先删除分量内外键。
3. 按 CREATE 流程重建表、索引和外键。
4. 每个阶段记录已完成对象，失败时返回明确阶段和对象信息。

## 5. 外键冲突策略

首版建议固定为：

- 名称和完整定义一致：跳过；
- 名称相同但定义不同：失败；
- 名称不同但完整定义相同：跳过或记录警告；
- 源端不存在而目标端存在：首版不自动删除；
- 外键添加因已有脏数据失败：失败，不静默忽略。

后续再增加显式的 `REBUILD`、`DROP_ORPHAN` 等策略，不将它们隐式绑定到 `TargetMode`。

## 6. 数据阶段的单独决策

结构迁移完成后仍需决定外键何时启用：

- 写入前启用：普通依赖按被引用表优先写入；
- 写入后启用：允许暂时违反约束，但添加外键前必须做数据校验；
- 循环数据依赖：需要可空列、分阶段写入或数据库专用延迟约束。

该决策不应由 `JdbcTableTarget` 单表 API 隐式推断。

## 7. 分阶段计划

### P0：元数据正确性（已修复）

- 字段映射保留并转换主键、外键、索引和表约束。
- 本地约束字段未映射时立即失败，避免生成不完整定义。
- 增加单元测试覆盖字段改名和元数据保留。

### P1：纯规划器

- 新增不可变的迁移计划 DTO。
- 实现拓扑排序、循环检测和强连通分量输出。
- 不执行 SQL，先完成确定性单元测试。

### P2：结构执行 MVP

- 新增独立的多表结构迁移任务/执行器。
- 扩展 `DatabaseDialect` 的外键创建和删除 SQL。
- 支持 MySQL、Oracle、SQL Server 的等价跳过和冲突失败。

### P3：REPLACE 与真实数据库验证

- 实现逆依赖删除和显式重建策略。
- 覆盖无环、循环、已有外键、冲突外键和脏数据失败。
- 使用真实 MySQL、Oracle、SQL Server 做集成验证。

### P4：多表数据迁移（另立任务）

- 定义表间数据迁移顺序、失败恢复和循环数据策略。
- 不与 P2/P3 合并，避免扩大现有 ETL API 的职责。

## 8. 工作量与验收

- P0：已完成，属于低风险修复。
- P1：约 1～2 人日。
- P2：约 3～5 人日。
- P3：约 4～8 人日，取决于真实数据库环境和权限。
- P4：约 5～10 人日，需单独评审公共 API。

P2/P3 验收要求：无环和循环依赖均能完成结构迁移；重复执行不会重复创建等价外键；冲突和脏数据失败可定位；现有单表 `JdbcTableTarget` 行为和公共 API 保持兼容。
